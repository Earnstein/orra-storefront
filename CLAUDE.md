## Project state

Next.js 16 (App Router, `src/`, `@/*` → `src/*`) e-commerce app. Storefront UI (homepage, product pages) is built on a Postgres catalogue (products, categories, stock); Better Auth has email + password configured (passwords, sessions, reset email, deletion, rate limits) with sign-in, sign-up, password reset, a header account menu and the account page, plus admin roles and an `/admin` area (M6, in progress: roles, the shell, product and order management, the public demo admin and its nightly reset); the bag lives on the server, checkout holds stock and takes Stripe test payments, and paid holds become orders with a confirmation page, email and order history (M5). Tests: Vitest unit tests and catalogue query tests against PGlite. Package manager is **npm**.

## How we ship

Roadmap and process: `docs/superpowers/specs/2026-10-04-roadmap-to-live-design.md`. Each milestone gets its own plan in `docs/superpowers/plans/` (M2–M7 also get their own spec), approved before any code is written.
- One module = one branch (`feat/…`, `fix/…`, `docs/…`, `chore/…`) = one PR, assigned to its GitHub Milestone; the PR template's checklist must be complete.
- The user approves by **squash-merging**; never merge PRs yourself. Every `git push` needs the user's approval.
- When a milestone's last PR merges: tag `vX.Y.0`, publish a GitHub Release, add an entry to `docs/milestones.md`.
- Stage files by path (never `git add -A`); the user installs things in the working tree in parallel.
- Environments: CI (`.github/workflows/ci.yml`) builds and tests on a throwaway, expiring `ci-*` Neon branch with credentials masked. Vercel previews get their own Neon branch via the Neon integration and are migrated, have their accounts (copied from production) deleted straight away (`db:clear-accounts`, which refuses anything not confirmed as non-production: `clearAccountsGuardError` in `scripts/db-target.ts`), and are **seeded**; production is migrated but never seeded by a build (`vercel.json` → `scripts/vercel-build.ts`, steps in `vercel-build-steps.ts`). **Exception (M6):** the nightly demo reset re-seeds production's catalogue every night (see Demo reset), so on the demo, catalogue changes meant to last go into the seed (`src/db/seed/catalog.ts`); `db:seed` itself still refuses production without `-- --production`. A preview build stops before touching any database unless `DATABASE_URL`'s host differs from `PRODUCTION_DB_HOST`, so it can never migrate or seed production.
- Local development uses the Neon `dev` branch. `.env.local` sets `DATABASE_URL` to it, and Next, the npm `db:*` scripts and the seed script read `.env.local` before `.env`. `.env` keeps production's URL plus `PRODUCTION_DB_HOST`, which `db:seed` and `db:migrate` check (`scripts/db-target.ts`). They refuse production unless run with `-- --production`, which in turn refuses any database that isn't confirmed as production. Both print which database they're about to touch. `npm run db:seed -- --check` prints which database `DATABASE_URL` points at, and must say `not production` before local database work. Worktrees symlink both files; never read them.

## Architecture

**Env** — `src/lib/env.ts` validates with Zod. `serverEnv()` is a function that parses on call (throws if invalid). Client code reads no `NEXT_PUBLIC_*` vars: the browser auth client calls its own origin, and Stripe's publishable key (`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, named for Stripe's convention) reaches the browser in `startCheckout`'s answer at runtime. `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` and `STRIPE_WEBHOOK_SECRET` are optional and must be **test-mode** keys (`sk_test_`/`rk_test_`, `pk_test_`; the store promises no real money); `paymentsConfigured(env)` needs the first two. `authBaseUrl(env)` keeps `BETTER_AUTH_URL` on production and locally, but on Vercel previews (where `BETTER_AUTH_URL` points at production) uses `https://$VERCEL_URL`, and `trustedAuthOrigins(env)` trusts the preview's branch URL too; `BETTER_AUTH_URL` is only optional on previews. `RESEND_API_KEY`, `EMAIL_OUTBOX_DIR`, `BLOB_STORE_ID` and `BLOB_WEBHOOK_PUBLIC_KEY` (Vercel Blob, for admin photo uploads: set by connecting the store, which authenticates with Vercel's rotating OIDC token, no long-lived secret; `uploadsConfigured(env)` needs both) are optional, and empty values count as unset. Because `src/lib/auth.ts` calls `serverEnv()` at module load, `next build` fails without server env vars — this is intentional. Copy `.env.example` → `.env.local`.

**Database** — `src/db/index.ts` exports `db` (Drizzle on the Neon HTTP driver, `casing: "snake_case"`) and imports `server-only`. All table definitions live centrally in `src/db/schema/`, one file per domain, re-exported from `src/db/schema/index.ts` (drizzle-kit and the `db` client both read that barrel). Migrations output to `./drizzle` (use `db:generate` + `db:migrate`, not `push`). `drizzle.config.ts` must keep `casing: "snake_case"` to match the client. Scripts outside Next (e.g. `scripts/seed-catalog.ts`) build their own client, because `server-only` can't load there.

**Auth (Better Auth)** — the config is split in three so the `server-only` guard can stay on the db client:
- `src/lib/auth.options.ts` — shared options. **Add auth methods and plugins here**, never in `auth.ts`, or `auth:generate` won't create their tables. `nextCookies()` must stay the last plugin.
- `src/lib/auth.ts` — the real instance (`server-only`, real `db`, secret/baseURL from env). Exported `auth` and `Session` type.
- `src/lib/auth.cli.ts` — used only by `auth:generate` (placeholder db). The Better Auth CLI refuses any config that imports `server-only`, even transitively. Never import it from app code.
- `src/lib/auth-client.ts` — browser client (`better-auth/react`); `src/app/api/auth/[...all]/route.ts` mounts the handler.

`src/db/schema/auth.ts` is generated by `auth:generate` (re-exported from the schema barrel) — regenerate it after adding auth methods/plugins, then `db:generate` + `db:migrate`; don't hand-edit it.

Settings (M4 spec): passwords 8–128 (`PASSWORD_MIN`/`PASSWORD_MAX` in client-safe `src/lib/auth/password.ts`); sessions 30 days (`rememberMe: false` makes a browser-session cookie); a signed 5-minute cookie cache; reset tokens last 1 hour and a reset revokes every session; `deleteUser` on, and a `hooks.before` refuses `/delete-user` without a password (`PASSWORD_REQUIRED`; Better Auth alone accepts a session under a day old); email verification not required. Rate limits live in the `rate_limit` table (`storage: "database"`; in-memory does nothing on serverless) with custom rules for `/sign-in/email` (5/min), `/sign-up/email` (3/min) `/request-password-reset` (3 per 15 min), and `/change-password` and `/delete-user` (5/min each, since both check a password), while `/get-session` is exempt (every page's header reads it; counting it would add a database read and write per page view); `auth.ts` turns them on only when `VERCEL_ENV` is production or preview (off locally and in CI, where tests share one IP). Things that need env or server-only modules are set in `auth.ts`, not the options: `sendResetPassword` (`resetPasswordSender(sendEmail)`), `rateLimit.enabled`, and `advanced.backgroundTasks.handler`, which hands Better Auth's deferred work (such as the reset email) to Next's `after()`, so a reset request answers as fast for unknown emails and the work isn't cut off on serverless.
- **Cookie cache lag:** browser session reads (`useBrowserSession()`, `/api/auth/get-session`) accept a session revoked elsewhere for up to 5 minutes. Server-side checks skip the cache (below), so a revoked session can't act; `advanced.database.joins` reads the session and its user in one query (`auth.test.ts` counts it).
- **Browser session** (`src/lib/auth/browser-session.ts`): every page reads who is signed in with `useBrowserSession()`, a TanStack query (`["session"]`) over `/api/auth/get-session` that returns `{ id, name, email }` or null; `recheckSession(queryClient)` re-reads it without the cookie cache. Until the component reading it has hydrated it reports pending (as the server rendered it): Next hydrates a page in pieces, and the header's read can finish before a later piece hydrates, which would make that piece's hydration mismatch (React then re-renders it, losing clicks). It's read once per page load (`refetchOnMount: false`), again on focus, and when another tab signs out (`markSignedOut()` writes `orra:signed-out-at`) or renames (`announceSessionChange()`): the `storage` event makes other tabs re-read it (Better Auth's client only broadcasts while its own session store is in use). Better Auth's client (`auth-client.ts`) is imported only by the sign-in, reset and account forms, and by sign-out on demand, so it isn't part of every page (M4's budget check found accounts had added 54 KB of JavaScript to every page and 290 ms to the product page's LCP on a throttled phone).
- **Data access layer** (`src/lib/auth/session.ts`, server-only): `getCurrentUser()` (`{ id, name, email }` or null; `getCurrentSession()` adds this request's session id; `getSession` with `disableCookieCache: true`, deduplicated per request) and `requireUser(returnTo)` (redirects to `signInPath(returnTo)`). Only `/account` pages (under `<Suspense>`), server actions and route handlers call them, so other pages stay static; each action and handler checks the session itself.
- **Roles (M6)** (`src/lib/auth/permissions.ts`, client-safe): Better Auth's `admin` plugin (`admin({ ac, roles, adminRoles: ["admin"], defaultRole: "user" })` in `auth.options.ts`, migration `0011`: `user.role`, `banned`, `ban_reason`, `ban_expires`, `session.impersonated_by`). Our statements add `product` (`create`, `update`, `archive`, `upload`) and `order` (`read`, `read-details` = unmasked name/email/address, `fulfil`, `cancel`) to the plugin's `user`/`session` ones. Roles: `admin` (the owner: everything, including the plugin's user and session endpoints), `demo-admin` (all product actions, `order: read`; no user or session actions, so the plugin answers 403), `user` (nothing; every new account, and a sign-up that sends a `role` is refused with 400; accounts from before roles have `null`, read as `user`). `roleCan(role, permission)` (comma-separated roles as Better Auth stores them; an empty permission is never granted) and `adminRoleOf(role)` are pure, for server checks and the UI. `getCurrentSession()` now also returns `role`. `npm run auth:generate -- --yes` (without `--yes` the CLI waits on an overwrite prompt).

**Search and results (M3)** — migration `0004` adds `products.search` (English `tsvector`: name weight A; colour, colour family, material and category name B; description and detail values C) and `products.search_text` (lower-cased name, colour, colour family, material and category name, for typo matching), both kept current by triggers: `products_search_refresh` (before insert/update) and `categories_search_refresh` (a category rename re-saves its products). A generated column can't read the category's name. The schema gives both an empty default that the trigger always overwrites, so inserts never set them; `pg_trgm` is enabled, and PGlite needs it loaded (`createPGlite()` in `src/test/pglite.ts`).
- `buildSearchQuery(q)` (`src/lib/catalog/search.ts`) keeps only runs of letters and digits (capped at 100 characters), ANDs them, and matches the last word as a prefix. Fixed vocabularies (audiences, colour families, materials) live in `src/lib/catalog/vocabulary.ts`; the database enums are built from them, so client code can validate values without Drizzle.
- `src/lib/catalog/filters.ts` holds the request model (`ResultsQuery`, `Filters`, `Sort`, `PRICE_BANDS`) and its rules: `hiddenFacets` (a page doesn't offer filters it fixes; category is only offered on search), `sortsFor`/`defaultSort` (relevance only on search) and `normaliseQuery` (drops values outside each vocabulary, rebuilds the scope from its own fields, reduces search text to its words, keeps a tab only on New/Women/Men, clamps the page to 1…`MAX_PAGE` (100), and sorts and deduplicates, so equal requests share a cache entry and no URL value reaches SQL unchecked).
- Results carry `ProductSummary` (`types.ts`: slug, name, price, stock and only the card image; `productSummaryColumns`), not the full `Product`, so listing payloads and each listing page's embedded data stay small (about 270 bytes per product). `ProductCard` takes a `ProductSummary`.
- `getResults(query)` (`src/lib/catalog/results.ts`) normalises, then a cached read (`"use cache"`, `catalog` tag and lifetime) returns the first `page × 24` products, the total, and counts per filter option. Two queries run in parallel: products with `count(*) over ()`, and one `UNION ALL` of grouped counts where each facet applies every filter except its own. A product matches a search when **every word** matches, by full text (the last word as a prefix) or, for words of 4+ letters, by a near spelling (`word_similarity(word, search_text) >= TYPO_THRESHOLD`, 0.45; pg_trgm's 0.6 default misses "lether"). Stop words don't constrain the match, but a stop-words-only query matches nothing. Relevance ranks by `ts_rank_cd`, then similarity, then newest. The explicit threshold means the trigram index isn't used (the indexable `<%` operator reads a session setting the Neon HTTP driver can't keep); fine at this catalogue's size.
- `GET /api/products` (`src/app/api/products/route.ts`) serves `getResults` (or, with `?slice=1`, `getResultsPage`: page `?page` on its own) to the client: `?collection=…` (plus `?tab=…` on New, Women and Men) or `?q=…`, then the same URL keys as the pages. Unknown collections or tabs return 404 JSON; any other bad value is dropped by the parsers. It sends `Cache-Control: public, s-maxage=300, stale-while-revalidate=600` and `Server-Timing: db;dur=…`. `resultsApiPath(query)` builds its URL with keys in a fixed order and defaults left out, so equal queries share a URL.

**Caching (Cache Components)** — `next.config.ts` sets `cacheComponents: true`. Every read in `src/lib/catalog/queries.ts` starts with `"use cache"` and calls `cacheTag("catalog")` and `cacheLife("catalog")`, a profile defined in `next.config.ts` (`stale`/`revalidate` 300 s, `expire` one year, matching Next's default). It's stale-while-revalidate: after 5 minutes the next visit still gets the cached copy while a fresh one renders, so an edit shows from the visit after that. **Bag (M5)** — the bag lives in Postgres; pages stay prerendered.
- **Data:** `carts` (`src/db/schema/cart.ts`, migration `0007`: UUID `id`, `user_id` unique and nullable — null is a guest cart — cascading with the user) and `cart_items` (primary key cart + product, both cascade, `quantity > 0`). - **Reads:** `readBag(db, cartId)` (`queries.ts`) uses live stock (not the catalogue cache) as this bag sees it (`availableTo` in `stock.ts`: stock plus what the bag's own open hold took, and plus holds lapsed more than 2 minutes ago but not yet swept, used by every bag read and write and the merge): a line above stock is lowered in the same request and marked `reduced`; a line with no stock stays, marked `sold-out`, out of the count and subtotal. It's one statement (the lowering in a CTE, the read taking lowered quantities from it), since each statement is a Neon round trip: `GET /api/bag` is two (the cart, then the bag) for its 50 ms budget, and a unit test counts them. `GET /api/bag` (`private, no-store`, `Server-Timing`) returns the `Bag` (`types.ts`) and corrects the count cookie.

Each change is one SQL statement (`mutations.ts`; Neon HTTP has no interactive transactions); the add is an upsert whose conflict update reads stock through a scalar subquery on `EXCLUDED.product_id` (an `ON CONFLICT` update can't see the `INSERT … SELECT`'s tables) and answers `capped` when less than asked was added. The 50-line check reads the statement's snapshot, so simultaneous adds of different products can pass it by a line or two. Prices never come from the client.

The browser store (`store.ts`, `useBrowserBag()`) now keeps only signed-out saved items (and those old lines until imported); its pure rules are in `rules.ts`.

**Checkout (M5)** — stock is held while the shopper pays; Stripe only authorises, and fulfilment (module 5) takes the money.
- **Payments** (`src/lib/payments/`): the app imports only `PaymentProvider` (`types.ts`: `startPayment`, `resume`, `verify`, `settle`, `undo`, `parseWebhook`; `InvalidWebhookError` → 400, `PaymentsUnavailableError`); `paymentProvider()` (`index.ts`) returns Stripe once its keys are set. `stripe.ts` (`stripe@23`, API pinned `2026-09-30.endive`): a Checkout Session in `ui_mode: "elements"` with `capture_method: "manual"`, line items priced from the hold, `expires_at` = the hold's, US shipping, `phone_number_collection`, `excluded_payment_method_types` = every type but `card` (this API has no allowlist; a method Stripe adds later needs adding), no line-item images, idempotency keys `checkout/<id>` (Stripe refuses the same key with different parameters, so a payment is only ever started from the hold itself, and an existing one is resumed: `resume` reads the open session's client secret, which is never stored), `settle/<ref>` (a refund has no fixed key: Stripe would replay a failed refund's error for 24 hours; a payment refunded in full isn't refunded again). `undo` expires an open session (re-reading it if it completed meanwhile), cancels an authorisation, or refunds. `fake.ts` is an in-memory provider for tests (it refuses the same checkout with different input, as Stripe does, and an undo of a payment already failed or expired does nothing).
- **Holds** (`src/db/schema/checkout.ts`, migration `0008`): `checkouts` (`open` | `fulfilled` | `expired` | `cancelled`, `expires_at` = now + 31 minutes, one open hold per cart by a partial unique index; `checkout_items(product_id)` indexed (migration `0009`) for `availableTo`; `cart_id`/`user_id` set null when the bag or account goes, so a hold can still be released) and `checkout_items` (name and price copied; products can't be deleted while referenced). `src/lib/checkout/holds.ts`: `takeStock` (locks the rows in id order, then one `UPDATE … WHERE stock >= q`, all or nothing: the caller rolls back on a short line), `createHold`, `findOpenHold`, and `releaseHold` / `releaseExpiredHolds` / `releaseCartHolds` / `releaseGuestHolds` (one statement: mark `expired` only if still `open` and return the stock, so a second release does nothing; the last two answer the payment references to undo). A lapsed hold is only swept, or counted as free by other bags, `HOLD_GRACE` (2 minutes) after it ran out: its Stripe session expires at the same moment, and a payment authorised at the last second must still find its hold. Transactions use `withTransaction` (`src/db/tx.ts`: Neon's WebSocket `Pool` per call, closed in `after()`; Node 22+ has the WebSocket); everything else stays on HTTP.
- **Starting** (`startCheckout({ email })`, server action in `actions.ts`, core `startCheckoutWith` in `start.ts`, tested with PGlite and the fake provider): find the bag → sweep lapsed holds (best effort) → read the bag (an emptied bag releases its holds and undoes their payments; empty → `/bag`) → payments configured? → a line just lowered, or nothing left to buy, answers `short` with the updated bag ("Only 1 Leather tote was left — your bag has been updated") → reuse an unchanged hold (same lines, prices and email) → else within the rate limit (`rate-limit.ts`: 5 new holds per IP per 10 minutes in Better Auth's `rate_limit` table, on Vercel only), in one transaction: use a matching hold another start just committed, or release the bag's holds, insert the new hold (first, so a concurrent start for the same bag waits on the unique index and then uses the winner's hold instead of finding its stock gone) and take the stock → resume or start the hold's payment (the reference is stored only while the hold is still open; a hold this request made is released if its payment fails, a found one never) → close the replaced holds' payments. Every release path (replacing, emptying, the sign-in merge) closes payments through `closeReleasedPayment` (`src/lib/payments/close.ts`), which first `verify`s: a payment authorised or paid in its hold's last seconds is left for fulfilment's lapsed-hold path (and logged), as is one it can't check. Stripe's return URL uses the request's origin when it's one of ours (a preview's branch URL; the cookies are host-only), else `authBaseUrl`. Answers `StartResult` (`ok` with `checkoutId`, `clientSecret`, `expiresAt`, `summary`, and the publishable key; or `short` | `empty` | `rate-limited` | `unavailable` | `email` | `failed`). Sets no cookies. Signing in releases a guest's open hold before the merge, and `auth.ts` undoes its payment after the response (`onHoldsReleased`).
- **`/checkout`** (static, `noindex`; `src/components/checkout/`): `CheckoutView` shows the gate (`CheckoutGate`: email, "Check out as a guest", "You can create an account after your order.", outlined Sign in to `/sign-in?returnTo=%2Fcheckout` carrying the email over) unless signed in; a guest's email is kept for the tab in session storage (`orra:checkout-email`). **Saved items (M4)** — signed out they live in the bag store's `saved` list; signed in, in the account.
- **Data:** `saved_items` (`src/db/schema/saved.ts`, migration `0006`): primary key (user, product), both foreign keys cascade, index `(user_id, created_at desc)`. Reads in `src/lib/saved/queries.ts` (`getSavedSlugs` newest first, `countSavedItems`, `getProductSummaries` in the order asked); writes in `mutations.ts`: `saveSlugs` keeps the newest `SAVED_LIMIT` (200, `limits.ts`) by deleting the oldest; `mergeSlugs` never deletes, adds only what fits and returns `unmerged`; `unsaveSlug`. Each step is one statement and safe to repeat (Neon HTTP has no interactive transactions and PGlite has no `batch`); times come from the database clock (`now()`); reads never return more than 200, so a save racing a merge can leave at most one hidden extra row until the next save trims it. The browser's own list is capped at 200 too (`toggleSaved` drops the oldest).
- **Server:** actions `saveItem`, `unsaveItem`, `mergeSaved` (`src/lib/saved/actions.ts`: session first, Zod (`isSlug`, at most 200), typed `ActionResult`); `GET /api/saved` (`{ slugs }`, `private, no-store`, 401 signed out); `GET /api/products/summaries?slug=…` (cards in the order asked, malformed and unknown slugs dropped, over 200 → 400, `public, s-maxage=300, stale-while-revalidate=600`, `Server-Timing`).
- **Client:** `useSaved()` (`src/lib/saved/use-saved.ts`) is the one hook (product page, `/saved`): `slugs`, `isSaved`, `toggle`, `status` (`local` | `loading` | `account`). Signed in it reads `["saved", userId]` (`slugs` newest first either way; `failed`/`retry` when the list can't load); a "signed out" answer while the browser still looks signed in (a revoked session within the cookie cache) re-reads the session without the cache, so it falls back to the browser's list; toggles are optimistic with rollback, serialised in click order (mutation key `["saved"]`, scope `saved`); each click flips the previous click's intent (a per-slug map set before `mutate`, since the optimistic list reaches React a render later), and the list is re-read only after the last one settles. Clicks while the session is still loading save to the browser (merged moments later).
- **Merge on sign-in:** `SavedSync` (mounted in `providers.tsx`) sends `mergeBatch(local)` (the newest 200 valid slugs, oldest first) once per user per page load, not on `/sign-in`/`/sign-up` (they navigate away and would cancel it), retrying twice; then removes from the browser what the account took and what can never merge, keeping `unmerged` and anything beyond the batch. Signing out never copies the account's items into the browser.
- **`/saved`** (static, `noindex`, client `SavedView`): "Saved items (n)", the cards (sorted request to the summaries endpoint, shown in saved order) with a remove control each (focus moves to the next card's Remove, else the heading); an error state with Try again; signed out, "Sign in to keep your saved items on every device"; empty, "You haven't saved anything yet" and New in. `/account`'s Saved items tile shows the count.
- e2e: `e2e/saved.spec.ts` (merge on sign-up, rapid toggles on a slowed network, rollback, sign-out, `/saved`, and the milestone's exit test across two browsers).

**Images** — `next.config.ts` uses a custom loader (`src/lib/image-loader.ts`): `images.unsplash.com` URLs are resized by Unsplash's CDN (width/quality/`auto=format` params), everything else goes through Next's optimiser. Store bare Unsplash URLs (`https://images.unsplash.com/photo-<id>`) with no size params. Next's optimiser has a hard 7s upstream timeout, which large remote originals hit under concurrent load — keep that in mind before routing a new image host through it.

**`cn`** — `src/lib/utils.ts` builds `cn` with `createCn` and registers the custom `text-*`, spacing and container names; otherwise class merging drops e.g. `text-caption` next to a text colour. tsconfig aliases the bare `"cn"` import to that file, so shadcn components (which `import { cn } from "cn"`) get it too. When adding a theme token in `globals.css`, add it to `utils.ts` as well.

## Gotchas

- drizzle-kit loads `.env` on startup, before `drizzle.config.ts`, and dotenv never overrides a value that's already set. Run bare, it ignores `.env.local` and targets production. That's why its npm scripts set `DOTENV_CONFIG_PATH=.env.local` and `db:migrate` runs through `scripts/migrate.ts`; `scripts/package-scripts.test.ts` pins this. Always use the npm scripts, never `npx drizzle-kit`.

- `scripts/fix-intent-bin.mjs` (root `postinstall`) re-points `node_modules/.bin/intent` at `@tanstack/intent`: TanStack Form's `@tanstack/devtools-event-client` ships a broken `intent` bin that npm links over it. If `npx intent` crashes with `ERR_PACKAGE_PATH_NOT_EXPORTED … intent-library`, run `npm install`. Delete the script once that package fixes its bin.
- npm 11 blocks dependency install scripts by default; warnings about `esbuild`/`unrs-resolver` postinstalls during `npm install` are expected.
- `@vitejs/plugin-react` currently fails to install (its optional Babel 8 peers conflict with shadcn's Babel 7); Vitest doesn't need it.
